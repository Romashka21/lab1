## Власна реалізація і межі

**DTO boundary.** Запит реєстрації приймає лише `RegistrationInput(UserName, Email, DisplayName, Password)`, вхід приймає `LoginInput(UserName, Password)`. Відповіді: `RegisterResponse(Id, UserName, DisplayName)` і `MeResponse(UserId, UserName, Role)`. У DTO немає ролі, id, власника, `PasswordHash` чи security stamp. Роль `Reporter` призначає сервер через `UserManager.AddToRoleAsync`, id генерує сервер. Для реєстрації перевіряються обов’язковість і довжина (userName ≤ 64, email ≤ 256 і містить `@`, displayName ≤ 120, password ≤ 128). Верхня межа пароля запобігає надмірно дорогому хешуванню. Додаткові поля в JSON (наприклад `role`, `id`) ігноруються, що перевіряє тест `T02_Register_ExtraRoleAndIdFields_AreIgnored_UserStaysReporter`.

**Звідки /api/me та create беруть id.** `GET /api/me` і `POST /api/incidents` вимагають автентифікації (`.RequireAuthorization()`) і беруть ідентифікатор лише з `HttpContext.User`, з claim `ClaimTypes.NameIdentifier`, перетвореного на `Guid`. Значення з body, query чи header (зокрема `X-Demo-UserId`) не використовується. У `POST /api/incidents` власник `Incident.OwnerUserId` встановлюється з principal, поле `ownerUserId` з JSON ігнорується.

**Cookie options і межа HTTP.** Фіксований профіль (scaffold): ASP.NET Core Identity, EF stores, схема `IdentityConstants.ApplicationScheme`, cookie `.AspNetCore.Identity.Application`: `HttpOnly = true`, `SameSite = Lax`, `SecurePolicy = SameAsRequest` у Development і `Always` в інших середовищах. Локальний запуск працює по HTTP, тому там атрибута `Secure` немає. Це не доводить роботу `Secure` у production, тому прапорець перевірено окремим тестом через HTTPS-клієнт. Я не відключав `HttpOnly`/`Secure`, щоб тест проходив.

**Фактичні flags.** Тест `Cookie_Flags_Https_HttpOnlySecureLax_Http_NoSecure` перевіряє заголовок Set-Cookie: через HTTPS є `httponly`, `secure`, `samesite=lax`, `path=/`; через HTTP є `httponly`, `samesite=lax`, `path=/`, а `secure` відсутній. У браузері (DevTools → Application → Cookies, `http://localhost:5080`) рядок `.AspNetCore.Identity.Application`: HttpOnly позначено, Secure порожній, SameSite Lax, Expires/Max-Age = Session. Значення cookie не показується.

**Строк дії.** Стандартний для Identity: cookie сеансова (без `expires`), серверна перевірка діє стандартні 14 днів зі ковзним продовженням. Я його не змінював. Закриття вікна не замінює logout, бо браузер може відновити сеансову cookie після перезапуску.

**Однакові login-відмови.** Для невідомого користувача і хибного пароля login повертає однаковий `401` без `Set-Cookie`, без `WWW-Authenticate` і з однаковою формою тіла. Причини Identity (чи існує акаунт) не повертаються. Автотест A-07 порівнює статус, Content-Type і стабільні поля JSON (`traceId` порівнюється окремо як діагностичний).

**Обраний duplicate-контракт.** Повторна реєстрація того ж імені чи email повертає `409 Conflict` (Problem Details з заголовком «Конфлікт реєстрації»), некоректні дані та слабкий пароль повертають `400` з `ValidationProblem`. Це усвідомлений компроміс: 409 підтверджує існування акаунта (канал перебору облікових записів). Тест `Duplicate_Register_SameUserNameOrEmail_Returns409_Consistently` перевіряє послідовність контракту.

**Rate partition/window/recovery і події.** Для `POST /api/auth/login` застосовано `RateLimiter` з політикою `login`: фіксоване вікно, ключ розбиття IP-адреса клієнта (`RemoteIpAddress`, при відсутності `"unknown"`), типове значення 20 запитів за 60 секунд, `QueueLimit = 0`, при перевищенні `429 Too Many Requests`. Значення читаються з конфігурації (`RateLimit:Login:PermitLimit`, `RateLimit:Login:WindowSeconds`). Тест використовує окремий host з лімітом 3 запити за 4 секунди: після 3 невдалих входів наступні запити (і для існуючого, і для неіснуючого користувача) отримують `429` однакової форми, після очікування вікна (4,5 с) вхід знову дає `204`. Подія автентифікації логується лише як тип події, результат і trace id; ім’я користувача записується тільки після успішного входу (при невдачі там може бути помилково введений пароль). Приклад: `Auth event login: result success, user bob, trace 0HNPA58VK7ULI:0000000D`. Пароль, cookie, hash, token, заголовок Authorization і тіло запиту в журнал не потрапляють.

**CSRF навчальний борг.** `SameSite=Lax` відсікає передавання cookie у частині міжсайтових запитів, що змінюють дані (наприклад POST з чужого сайту), але не є повним захистом: лишаються навігаційні запити верхнього рівня та сценарії в межах одного «сайту». Повний захист (antiforgery-токени, перевірка Origin) вводиться в ЛР 6. До того це задокументований навчальний борг. `HttpOnly` захищає від читання cookie скриптом, а не від CSRF, а CORS сам по собі CSRF не усуває.

**Обрані поглиблення.** (1) Готовність до оновлення хешу пароля (rehash). (2) Втрата чинності старого сеансу після серверної події (зміна security stamp). Докази нижче.

## Докази

Пояснення, що охоплює всі рівні.

**Маршрут довіри.** JSON-запит реєстрації → перевірка DTO → `UserManager.CreateAsync` (Identity перевіряє вимоги до пароля, сама обчислює хеш із сіллю і зберігає користувача в EF store) → безпечна відповідь `RegisterResponse`. Вхід: `POST /api/auth/login` → `SignInManager.PasswordSignInAsync` перевіряє пароль за збереженим хешем і при успіху додає `Set-Cookie` із зашифрованим квитком claims → браузер сам додає cookie до кожного наступного запиту → `UseAuthentication()` (authentication handler) розшифровує й перевіряє cookie та формує principal → `HttpContext.User` → endpoint із `RequireAuthorization()` бере id з claim `NameIdentifier` і використовує його як власника ресурсу.

**Стандартна перевірка пароля.** Пароль перевіряє `SignInManager`/`UserManager` через стандартний `PasswordHasher` Identity (PBKDF2 з HMAC-SHA512, 100 000 повторень, випадкова сіль 16 байт). Власного хешування (наприклад `SHA256(password + salt)`) я не писав. Хеш у відповідях API не повертається. Таблиця `identity_users` зберігає `PasswordHash` типу `text`, а колонки для відкритого пароля немає.

**Чому client UserId не є доказом особи.** Будь-який клієнт може надіслати чужий `UserId` у body, query чи header (наприклад `X-Demo-UserId` Боба). Доказом особи є лише principal, який сервер сформував із власної зашифрованої cookie, яку клієнт без серверних ключів не може підробити. У початковому коді `/api/me` довіряв заголовку `X-Demo-UserId`, тому після виправлення такий запит без cookie повертає `401`, а з cookie Аліси повертається профіль Аліси незалежно від заголовка.

**Endpoint-и перебору акаунтів і компроміси.** `POST /api/auth/register` розкриває існування акаунта (409), я прийняв це як задокументований компроміс і обмежив обсяг відомостей (відповідь не уточнює, чи збігся логін чи email). `POST /api/auth/login` не розкриває існування акаунта (однаковий 401, однакові 429), а ризик перебору паролів зменшує обмеження частоти. Обмеження за IP-адресою має недолік: користувачі за спільним NAT ділять один лічильник, тому на практиці його доповнюють іншими заходами (див. «обґрунтування ключа» нижче).

Обґрунтування partition key та виключених полів події: ключ розбиття IP-адреса обрано тому, що він не залежить від введеного імені, тому зловмисник не може «заблокувати» чужий акаунт, вводячи його ім’я (як було б із ключем за іменем користувача). Недолік: користувачі за спільним NAT діляють один ліміт, а розподілена атака з багатьох адрес його обходить. Ключ `email:password` не використано, бо password не може бути ключем розбиття. В подію автентифікації не потрапляють пароль, cookie, hash, token, заголовок Authorization і тіло запиту. Ім’я користувача пишеться лише після успішного входу, бо при невдалому вході поле імені може містити випадково введений пароль.

Поглиблення 1, пояснення. Перевірялося, що стандартний hasher впізнає хеш, створений із меншою кількістю ітерацій, і повертає `SuccessRehashNeeded`. Завдяки цьому система може перерахувати хеш за сильнішими параметрами під час наступного успішного входу, не змушуючи користувача змінювати пароль. Сіль унікальна для кожного хешу, тому однакові паролі різних акаунтів мають різні збережені значення. Критерій доказу: результат перевірки до і після зміни параметрів та різниця хешів, а самі значення хешів не друкуються.

Поглиблення 2, пояснення. Звичайний logout видаляє cookie лише у клієнта, який його виконав, і не відкликає вже скопійовані квитки. Security stamp у БД порівнюється зі значенням у cookie під час періодичної перевірки (за замовчуванням раз на 30 хвилин), тому після серверної події (скидання пароля, відкликання сеансів) старий сеанс втрачає чинність під час наступної такої перевірки, а не обов’язково негайно. Для демонстрації в тесті інтервал перевірки встановлено в нуль, щоб ефект було видно одразу. Це лише тестове налаштування, у застосунку інтервал не змінено.
