# F-03. Перевірка дубліката назви розкриває існування чужого інциденту (409-оракул)

**Статус:** Fixed (`8b36e73`)  
**Актив:** конфіденційність чужих інцидентів (політика «чужий = неіснуючий», A-10)  
**Компонент:** `POST /api/incidents` (`Scaffolding/Lab02Endpoints.cs`), `PUT /api/incidents/{id}` (`Presentation/Endpoints/IncidentEndpoints.cs`) — правило T-03  
**Пріоритет:** P2

Знахідка поза прямим checklist методички: знайдена власним аналізом меж (порівняння відповідей 404 у read-шляху і 409 у write-шляху для того самого чужого ресурсу).

## Передумови і межі огляду

- Commit відтворення: `ed0d876`, Development, стан після `-- --reset-database`.
- Акаунти: `alice` (Reporter) — атакувальник; `bob` — власник seed-інциденту `20000000-0000-0000-0000-000000000002` «Невідома спроба входу» (статус `InProgress`).
- Клієнт: Microsoft Edge 157, `auth-lab.html`, `browser-lab.html`.

## Відтворення

1. Alice: `browser-lab.html` → Guid `20000000-0000-0000-0000-000000000002` → **`GET: 404`** (S37). Політика A-10 працює: чужий інцидент не видно.
2. Alice: `auth-lab.html` → «Новий інцидент» з назвою **`Невідома спроба входу`** → **`409: Конфлікт предметного стану`** (S38).
3. Контроль: назва `Неіснуюча назва 12345` → `201` (S38).
4. **Expected:** відповідь на назву чужого інциденту не відрізняється від відповіді на будь-яку іншу назву.
   **Actual:** 409 лише для назв, які вже існують у **чужих** активних інцидентах.

## Вплив і ймовірність

**Статус перевірки:** спостережено локально.

Будь-який автентифікований Reporter може перебором назв визначати, які інциденти існують у інших користувачів (наприклад, перевіряти гіпотези «чи є інцидент про витік у відділі X»), хоча read-шлях за політикою A-10 це приховує. Аналогічно `PUT` перейменуванням власного інциденту. Ймовірність висока (достатньо звичайного акаунта й форми клієнта), вплив — розкриття факту існування й точної назви, без вмісту → P2.

## Першопричина

Правило T-03 (ЛР 2) перевіряло дублікат **глобально**: `db.Incidents.AnyAsync(item => item.Title == title && активний статус)`. Під час ЛР 4 видимість обмежили (`VisibleTo`, 404 на чужі), але write-перевірку не узгодили з read-політикою: запит виконувався поза межами власника.

## Виправлення

Коміт `8b36e73`:
- `Lab02Endpoints.cs`, рядок 142: умова `item.OwnerUserId == ownerUserId && item.Title == title && …` — дублікат шукається лише серед інцидентів того самого власника (власник — з перевіреного principal).
- `IncidentEndpoints.cs`, рядок 223 (PUT): `&& item.OwnerUserId == incident.OwnerUserId`.
- Там само (рядки 345, 403–414): аудит **дозволеного** triage `authorization.allowed … result=succeeded` у каналі `SecureLab.Audit` (доповнює наявний `authorization.denied`).
- Тест `Lab06DuplicateTitleTests.RegF03_DuplicateTitleCheck_DoesNotRevealForeignIncident_ButKeepsOwnConflict`.

## Retest

1. Після fix Alice: назва `Невідома спроба входу`, опис `перевірка F-03` → **`POST: 201`**, `GET: 200` (S40). Чужий інцидент більше не впливає на відповідь.
2. Автоматизовано (`RegF03_…`): POST з назвою чужого активного → 201; PUT власного з назвою чужого → 200; інцидент Bob не змінено — PASS.

## Positive regression

- Повторне створення **власного** дубліката `Невідома спроба входу` → **`POST: 409`** (S40): правило T-03 для власних інцидентів збережено.
- `T03_DuplicateActiveTitle_Returns409`, `T03_SameTitleDifferentCase_IsNotConflict` (ЛР 2) — PASS у фінальному прогоні.

## Залишковий ризик

- Analyst бачить усі інциденти й так, тож для нього 409 не є додатковим каналом.
- Бізнес-рішення «унікальність назви в межах власника» змінює семантику T-03 (раніше — глобальна унікальність); прийнято, бо глобальна унікальність несумісна з політикою A-10. Інші можливі оракули (час відповіді, розмір відповіді) не вимірювались.
